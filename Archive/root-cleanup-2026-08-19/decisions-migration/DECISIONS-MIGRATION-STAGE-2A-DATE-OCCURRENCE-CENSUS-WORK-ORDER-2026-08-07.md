### 0.1 Why this step is a completeness proof, not a listing

Amendment 1 Clause B §2.2 makes a rebinding valid only when the derived report proves four things. The first two — every concrete date-bearing occurrence maps to exactly one inventory row, and no occurrence is unmapped or multiply mapped — are bijection claims over a population. **This census is that population.** `M7.5` step 6 does re-derive the occurrence population over the completed file and prove the embedded report equals the regenerated one. But that is an equality between two outputs of the same matching rule: if the same implementation is reused, it reproduces an omission identically at both ends and the equality holds. Step 4, meanwhile, validates the architect's mapping *against this census* rather than against a fresh scan. A span that never enters this census is therefore assigned by nobody at step 3, looked for by nobody at step 4, and consistent with a passing step 6.

`M7.4` states the same requirement from the other side: the census covers every ISO date token in the completed manifest, not only those named in Part D, **including tokens in the manifest's own governance prose**, and any token no family claims is a finding returned to the architect seat rather than silently assigned or defaulted to fixed.

Two consequences bind this order. First, the census is over-inclusive by design: a span Codex thinks is obviously irrelevant is still a row. Second, completeness is proved rather than assumed, which is why §3 requires two independent derivations and §2.3 forbids silent rejection.

## 2. The census

### 2.1 Scope of the candidate

The candidate is the entire target file as it stands: byte `0` through EOF, inclusive of the terminal `@@ASSEMBLY_CURSOR@@` line and the final LF. **No section is out of scope** — the `M0` header and its `MIGRATION_DATE` binding declaration, `M1` through `M3`, all 65 `M4` records across all fourteen items, all thirteen `M5` archive wrappers, the whole `M6` omission register, the `M7` date-surface model, and the sentinel line itself.

Read the file as bytes. Every offset in the deliverable is a UTF-8 **byte** offset, not a character index and not a line-relative index unless the column field says otherwise.

### 2.2 Occurrence definition

`M7.1` defines one occurrence as one maximal ISO `YYYY-MM-DD` token span, where maximal means the span is not extended by an adjacent digit or hyphen that would make it part of a longer token, and is not subdivided into year, month, or day components. Operationally, and binding for this order:

A **candidate span** is any run matching `[0-9]{4}-[0-9]{2}-[0-9]{2}`. A candidate span is an **occurrence** if and only if:

- **(a)** the byte immediately before `start` is not an ASCII digit, or `start` is `0`; and
- **(b)** the byte immediately at `end` is not an ASCII digit, or `end` is EOF.

**An adjacent ASCII hyphen does not disqualify a span.** `M7.1`'s wording is awkward on this point, and the reconciliation comes from the rest of `M7` rather than from parsing that sentence harder. `M7.2` adjudicates which family claims the ISO date **inside the normalized archive filename**, which presupposes that a filename-internal span is an occurrence at all; `M7.4` makes the population every ISO date token in the manifest. Enclosing filename and anchor hyphens therefore do not destroy occurrence identity. The narrower point holds too: a hyphen cannot extend an ISO date into a longer ISO date, so nothing about maximality is lost.

The live file settles it concretely. `DECISIONS-ARCHIVE-2026-08-18.md`, `DECISIONS-MIGRATION-COMMISSION-AMENDMENT-1-2026-07-29.md`, and the `M5.5.x` item-8 pointer anchors ending `-2026-07-12-pass` all carry hyphen-flanked spans, dependent and fixed alike. A blanket hyphen-boundary exclusion would drop the largest dependent family in the file together with a class of fixed surfaces, and would drop them silently.

Three mechanical invariants follow, and each violation is a **BLOCKER** reported rather than corrected:

- every occurrence is exactly `10` bytes long;
- occurrences do not overlap;
- occurrence offsets are strictly ascending in the order reported.

**No calendar-validity filter is applied.** A span such as `2026-13-45` is still an occurrence if it satisfies (a) and (b); report it as an occurrence and flag it additionally as an **ADVISORY**. Whether a token is a real date is a semantic question, and this step decides no semantic questions.

**If Codex reads `M7.1` as requiring a different rule from the one written here, run the rule written here and report the disagreement as a finding.** Do not substitute a reading silently. An order that turns out to be wrong is repairable; a census run under an unrecorded rule is not.

### 2.4 Near-miss advisory scan — non-ISO date-like forms

`M7.4`'s completeness argument holds only for the token grammar the census actually scans. A date-dependent surface rendered in some other form would escape this census with nothing to mark its absence. Scan for, and report as **ADVISORY only**:

- runs of exactly `[0-9]{8}` bounded by non-digits;
- `[0-9]{4}/[0-9]{2}/[0-9]{2}`;
- `[0-9]{4}\.[0-9]{2}\.[0-9]{2}`;
- an English month name (full or three-letter abbreviation) adjacent to a one-or-two-digit day and a four-digit year, in either order.

Report each with byte offset, matched text, and its complete physical line. **None of these is an occurrence.** Do not add them to the TSV, do not number them in the occurrence sequence, and do not reclassify any of them on judgment.

**Expect noise rather than silence here, and do not suppress it.** An eight-digit run bounded by non-digits will fire on incidental numerals and on hexadecimal material whose flanking bytes happen to fall outside `0`–`9`, and this file carries a great many digests. That is harmless, because nothing in this order acts on this scan. A long advisory list is not a finding, a hit that looks like noise is still reported, and a null result is a real and useful result reported as measured.

### 2.5 Per-occurrence rows

The authoritative output is a single tab-separated block, one row per occurrence, with these ten fields in this order:

1. `occ` — sequential index from `1`, ascending by byte offset.
2. `start` — 0-based inclusive byte offset.
3. `end` — exclusive byte offset; always `start + 10`.
4. `line` — 1-based physical line number.
5. `col` — 1-based byte column of `start` within that line.
6. `literal` — the exact ten bytes.
7. `section` — the innermost manifest heading enclosing the span, given by that heading's own label (`M0`, `M4.45`, `M5.5`, `M6.3`, `M7.2a`, and `sentinel` for the terminal line). Derive it from the file's own headings.
8. `record_item` — for a span inside any numbered construction record, the number of the enclosing item; `-` everywhere else. This covers the 65 `M4` records and the thirteen `M5.5.x` wrapper records alike: `M4` records number items `1`–`14`, wrapper records number items `1`–`13`, and the number is reported as the record itself writes it. The rule is total by construction — a span is either inside exactly one numbered item of one record, or outside every record.
9. `container` — the enclosing markdown container, decided **positionally rather than semantically**, by this precedence with first match winning: `sentinel-line` if the span's line is the terminal `@@ASSEMBLY_CURSOR@@` line; else `fenced-block` if the line lies between an opening and a closing fence; else `heading` if the line's first non-whitespace byte is `#`; else `table-row` if the line's first non-whitespace byte is `|`; else `prose`.
10. `context` — the complete physical line the span sits on, untruncated.

**Why `record_item` is item-numbered rather than field-named.** Revision 1 asked for the wrapper *field name* in place of an item number, which left most wrapper spans with no defined value: `M5.5.1` alone carries spans in its item-3 heading, its item-4 `Date` field, its item-8 archive-index line and pointer anchor, and its item-12 boundary rationale, and item 8 carries several at once — the filename's dependent span, the `archived` prose span, and the anchor slug's fixed `2026-07-12`. None of those is a field name. Where a span *does* sit on a `- **Name:** value` line, `context` reproduces that line in full, so the field name is recoverable without a second locator column and without a second rule to disagree about.

**Why `container` is positional.** Revision 1 asked for a semantic classification — `filename`, `path`, `field-value` — which is a judgment, and this order bars this seat from judgment. It was also indeterminate: two correct implementations could disagree on it while agreeing perfectly on every offset, and §3 compares offset sets, so the disagreement would pass unseen. The positional test above is decidable from the line alone.

**`container` is descriptive locator data and nothing more.** It does not classify a span as target-document bytes, wrapper bytes, governance prose, dependent, or fixed, and it confers no family membership. Step 3 makes those assignments from the complete locator — `section`, `record_item`, the byte offsets, and the full `context` line — read against the manifest, never from `container` alone. The temptation is specific and worth naming: fenced blocks in this file do in practice carry target and wrapper bytes, while the surrounding prose carries this manifest's own governance text, which is the surface class `M7.2a` created family `D6` to cover. That correspondence is an observed property of the current bytes, not a guarantee this rule enforces, and a rationale that promised it would be handing step 3 a syntactic proxy for a semantic question.

**These are locators, not assignments.** Codex assigns no `D` or `F` family, no surface ID, and no dependent/fixed disposition. A row carrying any of those is a **BLOCKER** against this order. Grouping, deduplication, and collapsing identical literals are all forbidden: two spans with the same ten bytes are two rows.

**Every locator is read from the manifest itself** — not from a search preview, not from a prior receipt, not from `DECISIONS-MIGRATION-STAGE-2A-CANDIDATE-REGIONS-2026-07-29.md`, and not from the live-source packet. This is standing ruling 38, which was minted against the architect seat on 2026-08-07 for citing a span lifted from a truncated preview rather than from the manifest's own record.

## 3. Two independent derivations

Derive the occurrence set **twice, by two methods that do not share a matching implementation.** One regex scan over the byte string and one hand-rolled byte-walk state machine satisfies this; running the same regex twice does not, and neither does running the same scanner under two shells.

Report both totals and the result of comparing the two offset sets for exact equality. **Any divergence is a BLOCKER**: report the differing offsets and stop. Do not reconcile by preferring one method, and do not report a union or an intersection as the census.

The reason is stated so it is not mistaken for ceremony. This population carries Clause B proofs 1 and 2 and is the basis on which the architect performs the step-3 surface assignment. An error inside a single matching implementation reproduces itself perfectly on every later run of that implementation — including `M7.5` step 6's regeneration, whose equality proof would then hold over two identically incomplete populations. Two implementation-independent derivations protect the population *before* assignment, rather than relying on a later regeneration to discover an upstream omission it shares.
