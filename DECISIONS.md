# DECISIONS.md

The reasoning-and-state layer for Project Shrimp. `AGENTS.md` says *how* to work; `PROJECT-HISTORY.md` records *what happened*; this file holds *why the architecture is the way it is* and *what is still open* — the things that are expensive to lose because a fresh agent (or future Luke) will otherwise re-litigate them from scratch.

## Status conventions

Formalized per principle 27(c). Every principle and open-thread entry carries—or, for older entries not yet retrofitted, should eventually carry—an explicit status immediately after its heading or opening bold lead-in:

- **Status: ACTIVE** — currently binding; no narrower or later ruling has replaced it. This is the default, so an untagged standing principle is active.
- **Status: SUPERSEDED** — replaced by a later, cited ruling. Retain it verbatim rather than deleting it; the tag names the superseding entry.
- **Status: REVISIT** — open because a decision, source check, bank-impact survey, or ratification is pending. Do not treat the described behavior as settled without reading the entry's next step.

**Retrofit status (2026-07-12 docs-consolidation pass):** principles 1–27 are active as of this pass. None of the numbered principles is itself superseded; only narrower amendments or extensions within some principles are, and those carry inline history. The open-thread entries most likely to be mistaken for settled are tagged below. Mechanically tagging every remaining amendment and extension is unowned follow-up work, not a blocker for this pass.

## Standing principles

**1. Answer placement is owned by code, not the model.**
LLMs are biased samplers: they write the correct answer first and confabulate distractors around it, so correct answers cluster into early positions. An audit found option D correct in only ~3% of MCQs, where uniform would be 25%. The fix is not more prompt guard rails — it is a deterministic shuffle, seeded by item ID, applied at the promotion step, so placement is a verifiable transform rather than a behavior begged from a model. The same mechanism drives select-all correct options clustering at the top, so this governs positional bias across *all* item types, not just MCQ.

**2. The producer is never the checker.**
The program that generates or shuffles content cannot be the program that verifies it — a checker sharing a run or codebase with the producer cannot independently fail the producer's output. The only thing they may share is a pure, deterministic transform (e.g. the shuffle function) that the checker re-runs to assert equality.

**Principle 2 extension — spec-conformance is not content review, and neither seat can do the other's job (2026-07-09).** When Claude authors a remediation spec and Codex implements it, Claude cannot certify the implementation: it would be checking output produced to its own instruction, where *matches the spec* is not evidence of *is correct*. But a seat **blind** to the spec cannot certify it either — it has no null to fail against. So the two checks split rather than collapse. Content review of the patched artifact goes to the gate seat (Claude Code), whose ignorance of the spec is a *feature*: it re-derives each disposition from source prose and the standing rules instead of confirming that Codex did as it was told. Spec-conformance verification stays with the architect, the only seat that knows what was asked. The failure this prevents is concrete: the `>150 seconds` aPTT in Candidate 12B passed schema validation, the flowsheet gate, the applicator dry-run, and a 100% checker-seat adjudication of its source batch, because the defect lived in `parseMeasurementValue`'s comparator strip — in *code* — and the artifact-checking seat had no reason to read code.

**3. Deterministic core; LLM only for the irreducible semantic residual, capped.**
Counting, distributions, permutation integrity, template repetition — all have known nulls and belong in scripts that return identical verdicts every run. Reserve model judgment for what genuinely needs semantics (clinical inferability, distractor plausibility), run it only on items the deterministic layer flags, and cap the batch. Keeps verdicts reproducible and token spend bounded.

For the non-MCQ bias audit, this means an offline handoff rather than an integration: the repo emits a deterministic Gemini queue and prompt, validates returned JSONL, and merges semantic findings without allowing them to modify Layer A. No API key, live model call, or network dependency belongs in the repository.

**Principle 3 extension — proposal-only topic residual passes may use in-harness GPT-5 (Jun 18).** For the post-S01 residual topic rerun, in-harness GPT-5 adjudication is accepted instead of an external queue/ingest loop because the safety boundary is proposal-only output: complete dry-run manifest, exact category/topic diff preview, non-Gemini classifier metadata, and Luke approval of the exact manifest before any canonical write. This exception does not authorize Gemini classification, automatic `topics.ts` writes, or removing the stop gate.

**Topic licensing decisions from residual dry-run review (Jun 18).** `Skin & Wound Care` is shared across Basic Care and Comfort, Reduction of Risk Potential, and Safety and Infection Control so pressure-injury/wound staging, prevention, monitoring, and skin-integrity rows can keep their real NCLEX category instead of moving to BCC solely to reach the topic. `Transfusion & Blood Products` is a shared topic across Safety and Infection Control, Pharmacological and Parenteral Therapies, Reduction of Risk Potential, and Physiological Adaptation so transfusion reactions and blood-product roles do not scatter across weak cardiovascular/lab/procedural buckets.

**4. Rationales are position-agnostic — bilingual.**
A rationale references option *content* ("furosemide is contraindicated because…"), never a letter or ordinal/spatial position ("Option D", "the first choice"). A rationale that never names a position cannot carry a stale answer-key reference after a shuffle — so this invariant makes a whole bug class structurally impossible rather than something to catch each run. Enforced across English and Simplified Chinese (选项A, 第一个, 以上 …).

**5. Generated ≠ reviewed.**
Raw model output is never trusted study material. It stages in `banks-raw/`, passes validation + audit + source-check, then promotes to a canonical `banks/*.json` with a `BANK-REVIEW-LEDGER.md` entry. The generating model never reviews its own batch; cross-model review precedes promotion. Gemini in particular is a raw-volume source only — small batches, never direct canonical edits.

**6. Visuals are deterministic, data-derived, and necessary.**
Every visual renders locally from inspectable structured data — no raster assets, no external images, no AI-generated medical imagery. A visual whose removal leaves the answer unchanged is decorative and therefore invalid. Each renderer ships with `selfCheck` cross-consistency assertions and registry conformance tests.

**7. Precision over volume.**
In any audit, five fully-evidenced findings beat thirty probable ones. Verbatim evidence, an honest reconciliation attempt, and explicit confidence/dismiss discipline are the standard (see the adversarial audit spec).

**8. Clinical truth is authored once, upstream, and read-only downstream.**
In the forward case-skeleton pipeline (Opus hub authors an English prose case -> GPT fact-checks clinical accuracy/currency and compiles to schema -> Gemini reviews with flags only -> Claude reviews), the author model owns the fact pattern, the correct actions, and the rationale. The compiler translates and shapes into schema but never decides or alters which action is correct, and never introduces clinical claims absent from the skeleton; distractors are drawn from the skeleton's enumerated nursing errors. This keeps the compile step out of inventing medicine and preserves producer≠checker (principle 2) across the chain: author, GPT compile/check, Gemini review, and Claude final gate have distinct roles. A decision point too underspecified to yield an unambiguous item is dropped, not guessed. Validated end-to-end on the aGVHD case under the prior split (2026-06-11); updated to the GPT-compile/Gemini-review split on 2026-06-15.

**Principle 8 extension — bowtie synthesis zone is author-supplied (Jun 14):** The case-skeleton author may include an optional BOW-TIE SYNTHESIS section; when present, the compiler emits a standalone `bowtie` as a second top-level question alongside the `case_study` (`meta.count` 1 or 2). Bowtie is standalone-only, so its `stem` carries a self-contained synthesis vignette independent of the case_study exhibits. The author supplies in English prose: the most-likely condition + two competing conditions with "why wrong" notes; two priority actions + two wrong actions; two confirming parameters + two irrelevant parameters. The compiler assembles the three zones and translates — never choosing the condition differential, the priority action pair, or the irrelevant-parameter pool itself. This extends principle 8 to the synthesis zones whose distractor pools (the differential, the irrelevant parameters) the prior skeleton did not carry, keeping those clinical choices with the author rather than the weaker-supervised compiler. A malformed or absent BOW-TIE SYNTHESIS section produces only the case_study; the bowtie is omitted, never fabricated. Forward case artifacts using unfolding metadata require schema `1.6` or later and should declare the current authoring version from `NCLEX-Question-Schema.md`.

**Principle 8 extension — case completion is accounted, not assumed (Jun 15):** Forward skeletons author six decision points, one primarily per NCJMM step, and the compiler targets six embedded items. Six is a target, not a padding quota: a genuinely underspecified point may be omitted only with a specific entry in the raw `_compileManifest`. Promotion fails when authored points or bowties disappear without accounting, verifies manifest counts against actual output, and strips the manifest before canonical merge. Legacy 4–5 item cases are tolerated when faithful to their recovered skeleton; under-compilation is repaired through the normal cross-model pipeline, never by hand-editing canonical JSON.

**Principle 8 extension — Gemini is review, not compiler (Jun 15):** GPT is the forward baseline for
clinical fact-check/currency plus current-schema bilingual compilation, with provenance routed to the `gpt-`
lane. Gemini is demoted from compiler/lint to a flag-only review layer over GPT's raw artifact: structural
checks, `_compileManifest` faithfulness, bilingual/stale-translation flags, and obvious internal consistency
issues. Gemini never mutates JSON, skeleton prose, ids, answer keys, or Chinese translation. Its output is a
structured issue list for GPT to fix or Claude to adjudicate, and it never substitutes for Claude's final
clinical/content gate.

**9. The case-skeleton is English-only; bilingual generation is concentrated in the compiler.**
The hub harness drifts to Spanish and mangles schema, so the authored skeleton is English prose only — no JSON, no second language. All zh is therefore generated downstream by the compiler, which makes compiler zh-fidelity the single point of failure. Gate it: a deterministic CJK-presence check on every must-be-bilingual field — the inverse of the topic-CJK Tier-0 gate (which fails when CJK *is* present). A missing zh, or English left sitting in a zh field, fails loud before review. (The aGVHD cure pass cleared this by hand — every English edit carried a matching zh edit — but the check should be mechanical, not trusted.)

**10. Study sessions mirror the exam's content distribution; difficulty is exam-sim-only.**
A study session is a representative slice of the NCLEX-RN, not a flat random draw over whatever was generated. The default recommended practice session draws 50 questions (≈ the 52 scored content items of a minimum-length real exam, where the distribution actually resolves) weighted to the 2026 test-plan Client Needs distribution, with a within-category diversity penalty so no narrow topic or visual kind (the EKG-glut case) fills its category's slots, and a per-kind floor guaranteeing ≥1 of each well-stocked visual kind. Difficulty adaptivity is a *separate axis* — the real exam is CAT-adaptive on difficulty — and is deliberately deferred to a future exam-simulation mode; study mode never adjusts on difficulty. Case studies are excluded from the weighted draw (on the real exam they are a fixed allotment counted independently of the content-area percentages). Spec: `Archive/study-session-weighting-spec.md`.

**11. Visual arithmetic is a machine-checked gate, not a trusted assertion — and it carries no engine.**
For every visual kind whose answer turns on a computed value (`io_record` totals/balance, `medication_label` dose/volume/rate, `device_screen` pump math, and `burn_map` %TBSA/Parkland, all shipped), the load-bearing numbers are typed on the visual spec, the question's inputs and keyed answer live in audit-only `meta`, and `selfCheck` recomputes the answer from spec + meta and asserts exact equality (after a declared rounding wherever division is involved). A mismatch is a *build failure*, not a content note — a keyed value that disagrees with the recompute is a broken item. The recompute is deliberately small: each kind exposes an *enumerated* set of one-line, same-unit derivations. We do not parse free-text doses or build a unit-conversion/dosage engine; a derivation that would need cross-unit conversion (mg↔mcg, mg/kg, mcg/kg/min, body-weight dosing) is out of scope for that kind, not a reason to grow the engine. This is principle 3 (deterministic core) and principle 6 (visuals necessary) made concrete for the chart/label/screen tier; human review still owns clinical validity — is the keyed value the load-bearing cue, and is anything *else* accidentally unsafe.

**12. Author-side currency: closed-world construction + routed flags, never a changelog.**
The case-skeleton author (Opus hub) is frozen at its training cutoff and has no tools, so it cannot be made current — currency belongs to the independent scaffold fact-checker, with Claude performing final review. Two mechanisms keep the author's cutoff from corrupting output, neither of which tries to update the author. (1) Closed-world construction: when a decision turns on a protocol, threshold, or guideline value, the governing rule is stated inside the case as an order or clinic protocol, so the keyed answer follows from the stated rule and the item survives external guideline drift (precision #3). This is the primary lever — a closed-world claim costs the fact-checker nothing. (2) Routed currency flags: the author may append one sentinel-delimited `---REVIEWER-CURRENCY-NOTES---` block listing only the specific decision-relevant claims whose currency it doubts, each with a fact-check; the compiler strips it before JSON conversion. The block is the *only* channel for currency uncertainty (inline hedging violates OUTPUT VOICE) and is deliberately scoped to currency alone, not general author notes — a broad notes block would reopen the meta-commentary surface we closed across v1–v4 and become a place to offload resolve-or-drop work. We deliberately do NOT feed the author a "what changed since 2025" changelog: it is the reference-dump instinct in miniature — always partial, costly to maintain, and redundant with the independent currency pass. Test-plan structure is not at risk: the 2026 NCLEX-RN plan (effective April 2026) kept the 2023 category weights and the NGN/NCJMM model, renaming only Safety & Infection Control; the cutoff risk is confined to clinical-guideline content.

**21. Generation prompts for repo-reading instances carry the semantic floor, not the schema.**
When the generating model can read the repo (the parallel GPT deepen instances have GitHub read access to `AGENTS.md` and `NCLEX-Question-Schema.md`), the prompt defers all per-format *shape* to those docs and restates none of it. Inline it keeps only what the schema cannot infer: the semantic-quality floor (no-filler distractors; per-choice rationale for keyed answers *and* distractors; closed-world stems; no lazy "notify provider" key; unique ordered-response sequences; bounded highlight selection; gradeable closed-vocabulary blanks; clinical scope/monitorability; bilingual parity) plus the one mechanical caveat that is *not* auto-recoverable — a `correct` reference to a nonexistent id fails the whole item, where normalization silently repairs enum casing and `meta.count`. Restating schema shape in the prompt bought brittle, form-filling compliance and degraded clinical reasoning without improving validity; the repo docs plus the promotion gate already own shape. Validated 2026-06-22-b (GPT deepen round 3, the "trusted-agent" prompt): 29 items across 6 formats promoted with zero schema errors and zero normalizer structural changes, against the prior deepen batch that needed a deterministic fix script for `ngnSkill` casing and missing bilingual glossary fields. This is principle 1's "the fix is not more guard rails" and principle 3's deterministic-core / semantic-residual split applied to the generation prompt itself. Bound: these instances read the repo but cannot execute `validate-bank` or write to disk, so the prompt asks for a downloadable file and an in-chat self-check, never an executed gate — the real gate is the pipeline after the file lands. The per-format shape lines stay a cheap, targeted re-add if a future round regresses on one specific type; the default for repo-reading instances is minimal.

**22. Opus skeleton cases are GPT-provenance for review-conflict purposes.**
In the forward case pipeline (principle 8), GPT authors/validates the clinical fact pattern and owns schema compilation; the Opus hub contributes English prose only, stripped before compile (principle 9). The producer that principle 2 protects against self-review is therefore *GPT*, not Opus: an `opus*` case is checker-conflicted for GPT (and for Gemini's flag layer), but **not** for Claude — Claude may audit Opus skeleton cases without violating producer≠checker, because the clinical substance an audit evaluates is GPT's, not the prose author's. For deterministic routing (Layer A and the audit batch-draw), `opus*` ids tag producer `gpt`, tier `low` — identical to `gpt_case_`, which is what they effectively are. This does **not** extend to `claude_*` items Claude authored directly (e.g. `claude_moc_*` delegation items), which remain Claude-produced and route to a non-Claude reviewer. Corrects the prior literal-prefix defect where `opus_` matched but `opus1_`/`opus3_`/`opus24_` fell through to producer `mixed` / tier `medium`; the matcher is `/^opus\d*_/`.

**23. Exam-like presentation is a renderer concern; case identity and grading are not.**
The Pearson-style split layout (client chart left, active item right) is presentation only. A `case_study` stays one top-level session question — one `AnswerState.caseStudy`, one aggregate submit, one aggregate score; `grading.ts`, storage, SRS, progress, flags, adaptive, and summary all key on the top-level `question.id`. Per-part submit / true unfolding reveal is deferred: it needs a storage+grading redesign (per-part result/completeness state, synthetic ids) and is revisited only if real-session observation shows aggregate submit is the fidelity bottleneck.
*Stage visibility is cumulative and fail-open.* Both `stageId` and `answerableAfterStageId` show global exhibits plus all stages through the active part's stage (`slice(0, idx+1)`); an absent or unresolved reference shows **all** stages. Earlier chart data is never hidden — unfolding cases are cumulative, and a later part depends on earlier findings. Unresolved references are advisory only (`audit:stage-refs`, Tier-2 WARN) because the runtime fallback already protects the learner; graduating to a blocking gate waits until the bank stays clean and new case generation reliably emits valid refs.
*Split eligibility is by visual geometry, not item type.* Kept full-width (excluded from split): the calibrated wide tracings `rhythm_strip`, `capnography`, `fetal_monitoring` — a half-width pane breaks their `min-width:36rem` horizontal-scroll calibration. The standalone split allowlist is eight squarish/vertical or compacted-table kinds: `vitals_trend`, `lab_trend`, `medication_label`, `device_screen`, `burn_map`, `injection_site`, `io_record`, and `io_trend`. `io_record` rejoined after the session shell widened and its SVG table geometry was compacted to fit the desktop visual pane. `mar` remains excluded: one column per time-grid entry plus medication fields is still too dense for the side-by-side pane. `io_trend` (U11 spec §12) was deferred to a measured proof render rather than predicted: the composite chart-over-table came in at 600×452 for a 4-interval item and 600×504 at 6 — taller-per-width than the already-allowed 600×300 `vitals_trend`/`lab_trend` charts, but the standalone pane has no fixed height cap (it scrolls with the page rather than clipping), so the composite joins the allowlist with no density cap on interval count. Revisit only if content review finds a longer-than-6-interval item genuinely cramped. `bowtie` is never split (no `question.visual`; its three-zone diagram is the answer control and needs full width). Review surfaces (Summary, Developer console) render stacked / full-width read-through, not split. Live case studies use a horizontal chart-over-work layout rather than the standalone visual side-by-side grid.
*Content, not the renderer, gates the case payoff.* Only ~12 of 102 staged cases have clean part→stage mappings; ~88% fall to the all-stages fallback, so the chart-filtering benefit is currently small. Backfilling correct mappings — and authoring a real first stage for the 6 `gpt_*` cases whose first part referenced a non-existent `*_initial` stage (since removed to fallback) — is a clinical-judgment content lane verified by `audit:stage-refs`, deferred until dogfooding justifies it. Pure split/stage logic lives in `src/examLayout.ts` with `scripts/tests/exam-layout.ts` to lock the cumulative/fail-open invariant.

**24. Structured measurements are values-only exhibit presentation; identity and display resolve at the edges, not in storage (schema 1.8, ratified 2026-07-07).**
Optional `structuredMeasurements` on `CaseStudyExhibit` (both `caseStudy.exhibits[]` and `stages[].exhibits[]`), additive to `id/title/content/visual`. Shape is a wrapper of typed `panels[]` (`kind: "labs" | "vitals"`), each with applicator-authored `columns[]` (`id` + optional bilingual `label`; the label carries the source's panel/timepoint marker — "ED", "1600", "on admission" — and is **never** inferred from `sourceSpan` at render time) and allowlist-keyed `rows[]`. The wrapper (not a single `kind` per exhibit) is forced by two live facts: staged records mix vitals + stat labs + ABG in one panel, and labs vs vitals render differently (fishbone vs flat). A value stores only `value` (byte-exact source value) + `unit` (an *accepted input* unit for the key — the token `measurementUnitPolicy` consumes; byte-exactness of the original prose token is neither claimed nor stored) + optional `context: "post_intervention"`. **Not stored:** canonical value and display unit both derive at render via `measurementUnitPolicy` (`toCanonicalMeasurementValue` / `displayPolicyFor`) — storing derived copies invites the drift the single `roundTo` exists to prevent. A stored `displayUnit`, and GPT's proposed byte-exact `sourceUnitText`, were both rejected as fields no v1 consumer reads; each is additive later, and the literal source token is recoverable from the staged `sourceSpan` if a future lane needs it. Renders **beside intact prose** (supplement = GATE 3 / principle 8); prose reduces to a pointer **only** for pure-KV exhibits, fail-loud if a non-KV exhibit blanks prose. **No flags/ranges in v1** — a row carrying either fails validation, because every `refBand` in `lab_trend/defs.ts` is an unverified placeholder; bands wait on the reference-range lane. Non-rendered dispositions (`skip_serial`, empty extracts, `excludedValues`, `unitAliases`) are ledger/staging-only, never canonical. **Assay identity precedes rendering:** split `troponin_i`/`troponin_t` and `sao2`/`spo2` — as structured-measurement-only allowlist entries (a def source unioned into `measurementAllowlist.ts`, **not** added to the `lab_trend`/`vitals_trend` renderer defs, so the trend-plot key surface stays deliberate) — and fix the gate `spo2` synonym so `SaO2` no longer matches it, before any promotion — label, cutoff, and interpretation differ, and the `spo2` collision already caused a Batch 14/19 misclassification. **Fishbone (labs snapshots):** a labs panel whose analytes occupy a recognized skeleton (CBC / BMP / CMP) renders as a fishbone, **full or partial** — an isolated H/H is a valid partial fishbone, preferred over a flat report for workflow familiarity (necessity waived per the 2026-07-06 override); non-template analytes (LFTs, lone troponin, lactate) and all vitals render flat; trends never route here (excluded as `skip_serial`). The fishbone is a net-new renderer built as a **fast-follow** — the schema/applicator/promotion proof ships on the existing flat `renderDocTable`/`renderFieldPanel` primitives first. **Proof batch** = the 2 clean-KV records (replace path) + 3–5 reviewed single-panel prose/scattered records (supplement path); the rest promote only after the proof render validates. The applicator is a deterministic dry-run loader (match `caseId`/`exhibitId`, mutate, serialize, validate every target bank, regenerate census), consuming Batch 20 for the serial redo and **excluding failed Batch 19**. Density cap is deferred to the real proof render (instrument-before-building). Extends principles 6 and 8 to the flowsheet-snapshot tier.

**25. Necessity is a property of the artifact, not of every element in it: an additive element over a value-complete artifact is permissible (2026-07-09, Luke ruling).**
Principle 6 requires that a visual whose removal leaves the answer unchanged is decorative and therefore invalid. Read element-wise, that rule forbids any redundant presentation layer — including a chart drawn over a table of the same numbers, because a value table is an *informational superset* of the chart plotted from it (every value the item turns on is in the table exactly; the chart is a lossy projection). Read artifact-wise, the rule is about whether the *visual* carries information the stem does not state. The artifact-wise reading is correct, and the boundary is stated as a rule rather than granted case-by-case:

> **A redundant element is permissible when it is additive over a value-complete artifact** — the rendered visual carries every exact value the item turns on, and the redundant element adds a *reading affordance* (pattern, direction, crossover, divergence) rather than the sole cue. It never licenses an ornament that carries information absent elsewhere in the artifact, and it never licenses an artifact whose values the stem already states.

This supersedes the ad-hoc workflow-familiarity waiver granted to the fishbone on 2026-07-06 and subsumes it on stronger grounds: the fishbone qualifies because it *preserves exact values* (a partial H/H fishbone is value-complete), not because clinicians are used to seeing one. Vendor ubiquity is explicitly **not** a qualifying criterion — Epic's diverging I/O chart is one vendor's view, and `io_trend` (principle 25's first new consumer, schema `1.9`) earns its composite chart-over-table render because the table beneath it is value-complete, not because Epic draws it that way. Familiarity is a welcome side effect, never the warrant.

Two fences are load-bearing and travel with the waiver; without them the waived kind degrades into an existing kind with a picture on top:
- **The necessity gate is unchanged and still strict, at the artifact level.** For `io_trend`: an item is valid iff collapsing the series to a single net balance changes the answer. If any single-timepoint tally resolves it, it is an `io_record` item. The waiver relaxes *chart-vs-table*, never *visual-vs-no-visual*.
- **No exact-value items on a waived-element kind.** The table makes "what was the net balance at 1200?" renderable; authoring it is forbidden, because that item is `io_record`'s and authoring it would prove the trend kind redundant. Item briefs on `io_trend` are pattern-only: direction, divergence, crossover.

The reversal trigger is cheap and specific: if review repeatedly catches `io_trend` items answerable from one timepoint, the waiver is not the problem — the collapse gate is being ignored, and the kind closes to new content until it holds.

**26. A disposition that suppresses a check must itself be checked (2026-07-09).**
The exhibit-flowsheet gate's GATE 2 completeness advisory fires when source prose names an allowlisted analyte that is *neither keyed nor excluded*. `excludedValues` therefore silences that advisory by construction — the instant a value is excluded, the check that would have questioned the exclusion can no longer fire. `gpt_case_refeeding_syndrome_tpn_01/baseline_record` is the demonstration: sixteen `reason: "prior"` exclusions swallowed the entire PACU panel (Na 138, K 3.5, phosphorus 2.8, Mg 1.8, the CBC), the current panel retained vitals plus one point-of-care glucose and **no electrolytes at all**, and the record gated `0 FAIL / 0 WARN` on every excluded row. Refeeding risk is graded on baseline phosphorus; stage 2's phosphorus 1.3 / K 2.9 / Mg 1.3 is a delta from a baseline the flowsheet had deleted. The gate was silent exactly where it needed to speak.

Generalize past the flowsheet. Every disposition that *removes* a value from the checked surface — `excludedValues`, `skip_serial`, an empty extract, an off-allowlist drop — purchases its silence by moving the value out of the checker's view. Each therefore needs its own precondition, enforced by something other than the disposition itself. This is principle 2 applied to negative space: a producer that can silence the checker by asserting *nothing to see here* has become its own checker. The corollary for review sampling: the records carrying the most exclusions are the records the gate understands least, so exclusion count is a **positive** signal for checker-seat sampling, not a negative one.

**Amendment (2026-07-09, Luke rulings) — extraction disposition semantics, censored values, unit inference, and population.** Six rulings out of the Candidates 12/13 gate review. All are v1-scoped and all extend principle 24.

- **`post_intervention` is a reassessment marker, not a co-location marker.** Tag a value only when it is explicitly presented as a reassessment following an intervention directed at *that measurement*, or following a clearly framed treatment bundle. Do not tag unrelated co-located values merely because some therapy appears elsewhere in the same exhibit. The forcing case is refeeding `stage_2_update`: the only preceding therapy is TPN initiation, which is the *cause* of the derangement rather than a response to it, so its values are untagged; `stage_3_update` ("After interventions, repeat labs") is tagged. Under the loose reading the two stages render identically bolded and the marker stops discriminating — which is the whole of its value.
- **`prior` requires a same-key current value in the same record.** `prior` has always meant *an older value restated for comparison, where a current value for the same key also exists* (the CKD and vancomycin baseline-creatinine exclusions). When no current value for that key exists in the record, the exclusion is not de-duplication, it is deletion. A value labeled prior/baseline/PACU with no same-key current sibling routes to a `prior_no_current` review/fail path — never silently into `excludedValues`. Where the earlier value *is* the exhibit's only reading, it keys as the current column and the column label carries the source's marker (`PACU (6 h prior)`), which is what principle 24's columns are for.
- **Censored values are typed, never coerced.** A source that reports a bound (`aPTT >150 seconds`, `D-dimer >50,000 ng/mL`, `troponin <0.01`) is not reporting a number, and parsing it as one is silent auto-correction inside a fail-loud system. `parseMeasurementValue` now returns `null` on `/[<>≤≥]/`; a `value` carrying a comparator is a hard validation FAIL, never a strip. The representation is an optional sibling `bound: ">" | "<"` beside `value`/`unit` (absent = exact), with three consequences: sanity bounds become **one-sided** for bounded values, or every above-range D-dimer fails the gate that exists to catch typos; the SI parenthetical is suppressed, since converting a bound is meaningful but printing two of them is clutter; and a bounded value is never compared against `refBand`. The bound is transcribed, never adjusted — whether a facility's aPTT ceiling is 150 or 200 seconds is a reference-range question and belongs to `lab-reference-range-verification-spec.md`, not to the extractor. ## Other standing invariants

- Bilingual EN / zh-CN parity on all displayed text.
- `question.topic` is English-only — it is a navigational label, not study content (the target user's working English covers the topic; the translation does its real work in the stem, options, and rationale, where the medical terminology lives). Enforced in `validateBankObject` (Tier 0): CJK in `topic` fails loudly and is never silently stripped.
- **JSON quote hygiene is a parse-time gate, and JSON shape is edited programmatically — not retyped.** Structural tokens (keys, delimiters) are ASCII `"` (U+0022) only; smart quotes (“ ” ‘ ’) in structural position are invalid JSON and fail at `parseBankText`/`validate-bank` — the file cannot promote. Chinese quotation marks (“…”/「…」) are correct inside `zh` values; a literal ASCII `"` inside a string is escaped as `\"`. **The dominant corruption source is editing, not generation:** LLM-retyped JSON via the Edit tool either upgraded structural quotes to curly (opus12) or downgraded in-string Chinese speech marks to unescaped ASCII (opus3). Lesson: a schema-shape migration of raw banks is a deterministic transform — load/mutate/serialize, or `patch-raw.ts` (principle 15) — never a free-form hand-rewrite, because a serializer makes both modes impossible. The gate stays fail-loud (principle 3): malformed quotes are a mechanical parse failure surfaced with location, never silently auto-corrected. A scripted curly-quote *recovery* is allowed only parse-fail-only, diff-confirmed, raw-scoped — and must **verify, not assume**, that every U+201C sits in structural position (a value with a legitimate Chinese open-quote breaks blanket conversion; flag those for human resolution). The GPT compiler prompt owns emit-time correctness as defense-in-depth; Gemini's review prompt must never repair JSON in place; the Opus skeleton is English-only prose and out of scope.
- Question IDs are globally unique across bundled banks, including both top-level questions and embedded case-study leaf questions. This is gate-enforced by `audit:ids` because progress, flags, sessions, and answer history key by `question.id`.
- **Raw-draft filename prefix routes to its canonical bank by a fixed table; the single source of truth is `CANONICAL_PREFIXES` in `lib/canonical-routing.ts`.** Model-origin lanes: `gemini-`→`gemini-canonical.json`, `gpt-`→`gpt-canonical.json`, `claude-`→`claude-canonical.json`, `hard-cases-`→`hard-cases-canonical.json`. The forward skeleton-compile lane emits `gpt-` drafts because GPT is the baseline compiler; older `gemini-` routing remains for legacy Gemini-generated standalone batches. Visual-kind lanes: `burn-`/`capnography-`/`device-`/`io-`/`lab-`/`mar-`/`medlabel-`/`vitals-`/`visual-` each route to the matching `*-canonical.json`. The **eight per-kind** canonicals are **complete content sets, not active generation targets** — they are the original roadmap lanes and all sit frozen at schema `1.2`; generated cases may *feature* those visuals but never in the per-item load-bearing form those banks hold, so content generation does not add to them; their rows exist only so a stray draft still routes for the schemaVersion guard. **`visual-` → `visual-canonical.json` is the live visual bank and the only visual generation target** (schema `1.7`, 53 items as of 2026-07-09). A visual kind added *after* the original roadmap does **not** mint a per-kind canonical and does **not** add a `CANONICAL_PREFIXES` row — it promotes through `visual-`, which is why no `rhythm-`, `fetal-`, or `inj-` prefix exists despite those kinds shipping. `io_trend` (U11) follows the same route. Minting a new per-kind canonical would fragment the live bank and manufacture a closed set for no benefit. *(Clarified 2026-07-09 after the U11 spec initially proposed an `iotrend-canonical.json` that precedent does not support; GPT flagged the resulting doc conflict, and the fix was to correct the spec, not to carve an exception into this invariant.)*
- Canonical merges are deterministic and gated via `npm run consolidate`: staged promoted output in `banks/_promoted/` is routed, validated, schema-guarded, ID-collision checked, appended, recounted, serialized, and then consumed. Canonicals are never hand-merged.
- Runtime stays static, offline, and `file://`-compatible. No server or live model call after build.
- **Schema versions are an ordered token, not semver — the minor component never exceeds 9 (2026-07-09, Luke ruling).** Every version string must sort correctly under **naive numeric, lexicographic, and index** comparison. `"1.10"` satisfies only the last (`parseFloat("1.10") === 1.1`, which sits *below* the `1.7` pacer floor and the `1.2` visual floor; lexicographically `"1.10" < "1.2"`), so it is never minted. At `1.9` the next version is `2.0`. **A major bump carries no breaking-change implication** — it is an overflow digit, and the feature-floor ladder (`1.2` visual, `1.3` highlight, `1.4` bowtie, `1.5` rationale-visual, `1.6` unfolding case, `1.7` pacer, `1.8` structured measurements, `1.9` `io_trend`, `2.0` `bound` + `population`) reads continuously across it. Retroactively consistent: `1.0`–`1.9` already satisfy the rule, so nothing migrates. The reason the naming rule exists rather than only a comparison helper: **version strings leak out of code.** They sit in `meta.schemaVersion` of every exported bank, in `PROJECT-HISTORY.md` prose, in `NCLEX-Question-Schema.md`, and in the context windows of four models that reason about floors in natural language without ever calling a comparator. A `schemaVersionAtLeast(version, floor)` — the single legal comparison primitive, implemented over a **private** index into `supportedSchemaVersions`, throwing on unknown — protects the code; only the naming rule protects everything else. Both are required. Every floor in the codebase is a `>=` comparison, so `atLeast` is the only operation a caller ever legitimately needs; exporting a raw rank invites arithmetic on a version index. Choosing `2.0` without the naming rule merely postpones the trap to `2.10`, which at the observed bump cadence is months, not years.
- Schema changes are rare and deliberate.
- Shared visual numeric helpers have a **single definition**: `fmt`, `fmtNum`, and `roundTo` live in `src/visuals/primitives/graphPaper.ts`, and every kind imports them — none redefines them. This is a correctness property, not just DRY: one canonical `roundTo` means every arithmetic kind rounds identically, so two kinds can never resolve the same dose math to different values. Same single-transform discipline the shuffle function follows (principle 2).
- **Case-study exhibit ids share one namespace across the whole case, and `caseStudy.exhibits` may be empty (2026-07-13 ruling).** `validateCaseStudy` previously tracked duplicate exhibit ids with a fresh `Set` per array — one for the top-level `exhibits`, and a *separate* fresh set per stage — so the same id could repeat between the top-level array and a stage, or between two stages, undetected. Three canonical cases had shipped exactly that shape (`opus3_iv_potassium_safety_case_01`, `gpt_case_opus5_cdi_immunocompromised_01`, `gpt_r1_regen_case_celiac_01`), each with an entire stage's exhibits byte-for-byte duplicated into the top-level array — discovered only when the exhibit-flowsheet gate/applicator, which indexes canonical exhibits by `caseId/exhibitId` alone, hard-rejected the duplicate as "more than one match." The schema now shares one `seenExhibitIds` set across the top-level array and every stage. This also surfaced a second, independent bug: `App.tsx`'s `CaseChartPane` renders `caseStudy.exhibits` unconditionally in the "Client record" panel from the start of the case, separate from the progressively-gated `stages[]` "Updates" timeline — so a stage's content duplicated into the top-level array was visible to the student immediately, ahead of the stage that was supposed to gate its reveal, a spoiler bug independent of the flowsheet tooling gap. The fix for all three cases was to remove the duplicate from the top-level array and keep only the staged copy (content was verified byte-identical and un-promoted in every instance before deletion) — which left each case's top-level `exhibits` array empty. Since the renderer already treats an empty top-level array gracefully (`exhibits.length > 0 &&`), the schema's former "`caseStudy.exhibits` must include at least one exhibit" floor was relaxed to "the case must include at least one exhibit somewhere, either the top-level array or a stage" — a case whose entire opening content is meant to be stage-gated, with nothing permanently visible before the first stage unlocks, is a legitimate shape, not an error.
- Category targets are the 2026 test-plan weights, projectwide -- not uniform. `NCLEX_CATEGORY_WEIGHTS` (in `src/schema.ts`, re-exported from `sessionSampler.ts`) is the single source for both the weighted study draw (principle 10) and the generation backlog in `scripts/coverage-report.ts`. The coverage report formerly used a uniform `questions.length / categories.length`, so the bank was generated toward flat-eight balance while sampled toward the test plan -- two distributions for one bank. Both now read one map; under/over is measured against `weight * total` within NCSBN's +/-3 percentage-point tolerance. **Item-type** balance stays uniform by design: the plan weights Client Needs categories, not item formats, so even coverage across the seven types is the right target there.

**16. Answer-pattern bias is a presentation-layer problem first, a content problem only where shuffling cannot reach.**
Two distinct failure modes hide under "answer-pattern tell," and they have different owners. *Positional* tells — where the correct option sits, which dropdown index is keyed, which matrix column is correct, how shallow an ordered-response scramble is — are artifacts of how an item is *displayed*, carry no clinical meaning, and are fixed by a deterministic, ID-seeded permutation that provably preserves keys, IDs, rationale refs, and bilingual text. This is principle 1 generalized from MCQ option order to every non-MCQ structural axis: normalize display order, never rewrite content, to remove a positional tell. *Distributional* tells — SATA correct-count concentration, ordered-response template repetition — are properties of the item *content itself* and cannot be shuffled away (permuting options does not change how many are correct, nor how similar two stems are). These are the only bias findings that route to content authoring, and the lever is generation constraints on new items plus dilution over time, never mass edits to reviewed canonical content. The non-MCQ bias audit's `fix_class` encodes exactly this fork: `SHUFFLE_AT_PROMOTION` is mechanical and automatable; `REGENERATE` is a content-design backlog item. Verified by the 2026-06-12 rebaseline: deterministic normalization cleared every positional check globally (SATA position, dropdown index, matrix column/row, scramble depth all PASS), leaving only the two distributional families failing.

**Calcium is two analytes — total and ionized are never conflated, and identity is resolved before unit conversion (2026-07-05).** Total calcium (`calcium`, canonical `mg/dL`, normal ~8.5–10.5) and ionized calcium (`ionized_calcium`, canonical `mmol/L`, normal ~1.15–1.35) are distinct registry keys measuring distinct quantities (ionized ≈ the physiologically active free ~50% fraction), not unit variants of one value. Conflating them is a real clinical-safety error — a bare "calcium 1.2 mmol/L" is a normal *ionized* but a critically-low *total*. Three rules:
- **Label-driven routing; identity before conversion.** Explicit ionized markers (`ionized`, `iCal`, `iCa`, `free calcium`; ZH 离子钙 / 游离钙) route to `ionized_calcium`; `total`/`serum`/bare `calcium`/`Ca` route to `calcium`. Identity must resolve *first*, because the unit conversion depends on it: the same source unit `mEq/L` converts differently per key (total `mEq/L`→`mg/dL` ×2.0; ionized `mEq/L`→`mmol/L` ×0.5 — both divalent, different canonicals). This is the concrete proof the one sourced conversion table is keyed by (analyte, sourceUnit), never by unit token alone.
- **Ambiguity is flagged, never guessed (identity WARN).** GATE 4 dimensional sanity does *not* catch total/ionized confusion — their plausible ranges overlap, so a mis-routed value passes. A separate advisory WARN fires only on the genuinely ambiguous case: a *bare* calcium mention (no total/ionized qualifier) whose value is out-of-normal-band for total but in-normal-band for ionized (or vice versa). Explicit labels are trusted — a stated "total calcium 5.0 mg/dL" is a real critical value and does not WARN; only bare ambiguous mentions route to human adjudication. The extractor never auto-reassigns on magnitude.
- **Display and prose-normalization are per-key and never inter-convert.** Primary display honors each key's canonical (total → `mg/dL`; ionized → `mmol/L`, which is the standard US ionized form, not a paren). The prose-normalization lane preserves the total/ionized qualifier verbatim and **never** converts a value between total and ionized (different analytes, not unit variants); a bare-and-ambiguous calcium is a skip-with-reason, not a normalization target.

The rule is: *no format may fall below the depth its sampling path requires; above that floor, topic fit and item quality override census arithmetic, and no weak bowtie, matrix, or highlight is authored to close a gap.* **The rationale-visual carve-out is already ratified** (principle 19: explanation figures validate in exhibit mode, `selfCheck` answer-coupling does not run); only `AGENTS.md`'s absolute wording is stale, which is a documentation sync, not a softening. **Worktree isolation and clean-and-pushed are two different rules** — `AGENTS.md` already says to leave unrelated edits alone, while `CLAUDE.md`'s clean/pushed requirement exists because the content-generating instances read GitHub rather than disk. A dedicated branch does not fix a stale pushed snapshot.

*Sequencing.* The documentation-consolidation audit runs **after** Schema 2.0 is green, against a stable contract, and lands as its own patch with no functional code and no bank changes. An inventory taken mid-bump inventories a state that will not exist in a week, and acting on it early is precisely how a philosophical rewrite gets mixed into a version patch. The pass is authored from the **architect seat**: rule authorship is where seat separation exists in the first place.
