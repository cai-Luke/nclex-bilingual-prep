Within B, `null` is syntactically smaller but conflates an explicit instruction with a common malformed/placeholder value. Null currently fails validation and would need a new floor anyway. It offers no collision advantage beyond the object while giving weaker intent evidence. A full replacement union `{kind:"stage",id:"..."} | {kind:"baseline"}` is unnecessary: retain all existing string references. A separate Boolean `baseline:true` is D and introduces competing fields without improving the runtime result.

Strongest alternative is A with reservation enforced through question validation, raw gate and shared resolution, and explicit handling of pre-existing/imported/stored collisions. It can be safe within a newly constrained domain, but it is no longer merely a renderer/gate semantics change. It narrows previously valid stage IDs, needs a bank-impact survey and compatibility policy, and still cannot infer the origin of an unvalidated stale sentinel string. B pays a deliberate feature floor once and avoids this domain/history dependency. That is the smallest mechanically safe design across all listed states, not the shortest JSON spelling.

The exact-token scan found no `@@case-baseline` in stage-ID/anchor positions across 13 parsed JSON files under `banks/`, with no parse errors; see [token-collision-scan.json](token-collision-scan.json). This is a mechanical collision observation, not a semantic survey, a permanent namespace guarantee, or an estimate of baseline prevalence.
